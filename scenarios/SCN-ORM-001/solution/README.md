# SCN-ORM-001: Solution

## Root cause

The test user's group has one policy statement:

```
Allow group <test-operator-group> to read orm-stacks in compartment <compartment>
```

Oracle's own IAM policy reference for Resource Manager lists what
`read` actually covers for the `orm-stacks` resource-type:

> `read` → `INSPECT` + `ORM_STACK_READ`, covering `GetStack`,
> `GetStackTfConfig`, **`GetStackTfState`**, `ListStackAssociatedResources`

Source: [IAM Policy Reference, Resource Manager](https://docs.oracle.com/en-us/iaas/Content/Identity/Reference/resourcemanagerpolicyreference.htm), Oracle documentation.

`read` is the lowest verb in the table for this resource-type, one
step above `inspect`. Nothing in its name suggests it includes pulling
the full Terraform state file. But `GetStackTfState` is exactly the
operation the OCI CLI's `get-stack-tf-state` command calls, and it's
covered by `read`, not gated behind `manage`. A Terraform state file
is not "metadata about a stack." It's the full recorded result of
whatever that stack's configuration computed, including any value a
resource like `random_password` generated during apply.

## How to confirm it, step by step

Using only the test user's credential:

```bash
oci resource-manager stack get-stack-tf-state --stack-id <stack-ocid> --file state.json --profile <test-user-profile>
```

Look inside the resulting file for the `random_password` resource:

```bash
python3 -c "
import json
d = json.load(open('state.json'))
for r in d.get('resources', []):
    if r.get('type') == 'random_password':
        print(r['instances'][0]['attributes']['result'])
"
```

This prints the password in full, generated by a stack this user never
had `manage` access to.

## What this does and doesn't prove

It proves that `read orm-stacks` includes `GetStackTfState`, exactly as
documented, and that this is easy to miss if you assume "read" means
"look, don't touch" the way it does for many other OCI resource-types.
It doesn't prove a flaw in Oracle's platform: the verb table is public
and accurate, nothing about this required guessing or exploiting
undocumented behavior. It doesn't prove that every real stack has a
secret sitting in its state; it proves that if one does, `read` alone
is enough to get it out.

## Remediation

- Treat `read orm-stacks` as state-level access, not metadata-level
  access, when writing Resource Manager policies. Scope it as
  carefully as you would scope read access to a secret.
- Avoid letting sensitive values land in Terraform state at all when
  possible; use a secrets manager reference instead of a resource like
  `random_password` whose result lives in plaintext in the state.
- If a sensitive value must be computed by Terraform, treat every
  principal with `read orm-stacks` on that stack's compartment as
  having access to it, not just principals with `manage`.
- Scope Resource Manager policies to the narrowest compartment that
  contains only stacks that specific group should be able to read.
